# Level Background Specification

> Reference for anyone creating or updating background images for ATC-APP levels.
> Covers canvas size, aspect-ratio variants, positioning runways on the artwork,
> and how the game loads and scales the images at runtime.

---

## How backgrounds are rendered

The game uses a **cover-scale world container** — one fixed reference world of
**1920 × 1080 game units** centred on screen. The formula is:

```
worldScale = Math.max(screenW / 1920, screenH / 1080)
```

This means the background always fills the screen with no black bars.
On tall screens (portrait-ish phones) the sides of the background spill off-screen.
On ultra-wide screens the top/bottom spill off. **The playable centre is always visible.**

The background image is loaded as a Phaser texture and stretched to exactly
`1920 × 1080` world units. This means **1 pixel in the background = 1 world unit at 1× scale**.

## Folder structure

Backgrounds are generated by `scripts/process-backgrounds.ts` — you never
hand-place files here. Free levels (see `freeLevelLimit` in
`process-backgrounds.config.json`) land in the bundled app:

```
packages/app/src/assets/backgrounds/
  manifest.json          # generated — describes every file below
  16x9/
    level-1.png           # 1x fallback (bare name, no @1x suffix)
    level-1@1x.webp        # 1x preferred format
    level-1@2x.webp        # 2x preferred format
  20x9/
    level-1.png
    level-1@1x.webp
    level-1@2x.webp
  19_5x9/ …
  19x9/ …
  18_5x9/ …
  18x9/ …
  16x10/ …
```

Paid levels (`levelNumber > freeLevelLimit`) are routed to
`dist_remote_assets/backgrounds/` instead — same structure, plus
`manifest-paid.json` — and are **never bundled**; they're uploaded to the
private `game_assets` Supabase Storage bucket via `pnpm upload:paid-backgrounds`.
See `BACKGROUND_ASSETS.md` for the full manifest schema and runtime selection
algorithm, and `PAID_BACKGROUND_MIGRATION.md` for the upload flow.

Every level needs **at minimum a `16x9` variant** — the universal fallback
(see `assetLoader.getFallbackBackgroundKey()`). All other variants are loaded by
`getBackgroundKeyForDevice()`, which reads the device's actual screen ratio from
`getDeviceInfo()` and picks the matching folder.

## Required aspect ratio variants

| Folder   | Ratio       | Screens                                             |
| -------- | ----------- | --------------------------------------------------- |
| `16x9`   | 1920 × 1080 | Desktop, many tablets, TV — **required / fallback** |
| `20x9`   | 2400 × 1080 | Modern Android (Galaxy S-series, Pixel)             |
| `19_5x9` | 2340 × 1080 | iPhone 12–15 Pro, many mid-range Android            |
| `19x9`   | 2280 × 1080 | Various Android                                     |
| `18_5x9` | 2220 × 1080 | Samsung Galaxy S8/S9                                |
| `18x9`   | 2160 × 1080 | Older tall Android                                  |
| `16x10`  | 1920 × 1200 | Some tablets                                        |

You do not need all variants for every level. The loader falls back gracefully.
However, for a shipped level the minimum recommended set is:
**16x9 + 20x9 + 19_5x9** — these cover desktop, iPhone, and most Android devices.

## Master image spec

Every level's master (`raw_assets/level-N-master.png`) should be **at least
5048 × 3328 px** (aspect doesn't have to match — a larger or differently-
shaped source is fine, the crop just takes less of whichever dimension has
extra; only being _smaller_ than this causes upscaling). This is the only
place where size is authored — every ratio × dpr × format output below is
generated automatically from it by `process-backgrounds.ts` via a centered
crop; you never hand-extend a canvas per ratio.

- **Format**: PNG, 24-bit RGB (no alpha needed — the background always fills the world rect)
- **Color profile**: sRGB, ICC profile stripped
- **Compression**: none on the master — keep it lossless. `process-backgrounds.ts` handles final WebP/PNG compression on the generated outputs; compressing the master first just compounds quality loss.
- **Content placement**: since every ratio is centered on the same point, keep runways and other gameplay-critical content within roughly the central 80% of the canvas — the most-zoomed mobile ratios (`mobileZoom` in `process-backgrounds.config.json`, up to 1.25×) crop in tighter than the unzoomed ratios, so content near the edges may not appear on every device.

`process-backgrounds.ts` warns (doesn't block) if a master is **smaller**
than `expectedMasterWidth`/`expectedMasterHeight` in
`process-backgrounds.config.json` — treat that warning as something to fix
before shipping the level, not background noise. A master that's larger, or
a different aspect ratio, never triggers this warning.

### Why 5048 × 3328

Every (ratio, dpr) crop needs to come from at least that many real source
pixels, or the `@2x` output is just an upscaled `@1x` crop — soft, not
actually retina-quality. Worked backwards from the highest-resolution output
any ratio/dpr combination needs:

| Ratio   | dpr | Output size | Zoomed?                                                                                                                                                                                                                                                                |
| ------- | --- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `20x9`  | 2x  | 4800 × 2160 | no (zoom shrinks the _crop_, not the requirement — sized for zoom=1 so this stays correct even if `mobileZoom` config changes)                                                                                                                                         |
| `16x9`  | 2x  | 3840 × 2160 | no                                                                                                                                                                                                                                                                     |
| `16x10` | 2x  | 3840 × 2400 | no — slightly taller than 2160; a native master would need 2400px height. 5048×3328 accepts a minor upscale on this one ratio since it's the rarest target device class. If you need zero upscale everywhere, use 5048×2400 instead and update `expectedMasterHeight`. |

### Output canvas sizes (generated, not hand-authored)

| Folder   | Crop target (dpr=1) | Notes                                                      |
| -------- | ------------------- | ---------------------------------------------------------- |
| `16x9`   | 1920 × 1080         | Reference — most runway/waypoint verification happens here |
| `20x9`   | 2400 × 1080         |                                                            |
| `19_5x9` | 2340 × 1080         |                                                            |
| `19x9`   | 2280 × 1080         |                                                            |
| `18_5x9` | 2220 × 1080         |                                                            |
| `18x9`   | 2160 × 1080         |                                                            |
| `16x10`  | 1920 × 1200         |                                                            |

Each also gets `@1x`/`@2x` in the preferred format (WebP) plus a `.png` 1x
fallback — see "Folder structure" below for exact filenames.

## Placing runways on the background

**A runway needs its two threshold endpoints authored: `masterX1`/`masterY1`
and `masterX2`/`masterY2`** — pixel coordinates on the RAW MASTER image (the
same file `process-backgrounds.ts` crops from, e.g.
`raw_assets/level-4-master.png`). `GameScene` projects each point
independently through `projectMasterToWorld()` and derives the runway's
center, length, and direction from the projected points, every ratio, every
time.

**This must be two points, not one.** The background is stretched with
_different_ X and Y scale factors per ratio to force-fit each crop into the
fixed 1920×1080 world rect (visible in the in-game debug overlay as a
non-square `bg scale`, e.g. `0.400x0.500`). That non-uniform stretch changes
both the _length_ and the _angle_ of anything on the image — so a single
center point + a precomputed length/direction scaled by one factor is wrong
on every ratio except whichever one it was measured on. Projecting both
endpoints independently and re-deriving length/angle from the results is the
only approach that stays correct everywhere; a single point is fine for
_position_ (an isolated point has no length or angle to distort), which is
why the earlier single-point scheme looked right in testing but drifted
under review — position matched, length and angle silently didn't.

**Do not hand-measure a separate position per ratio**, and don't add a
per-ratio `positionOverrides` / `masterPositions` map back — both are legacy,
unused by the runtime, and reintroduce the exact per-ratio-drift problem this
whole scheme exists to avoid.

### How to find masterX1/Y1/X2/Y2

Use `scripts/generate-master-runway-coords.ts runway` (or `pnpm runway
runway ...`) — it does the pixel math for you against the actual generated
crop data:

```bash
# 1. Open the 16x9 output PNG (packages/app/src/assets/backgrounds/16x9/level-N.png
#    or the @1x.webp) in any image editor. Click the runway's TWO threshold
#    ends — start and end of the strip, in the direction of landing. Read
#    both pixel coordinates.

# 2. Convert both points in one command, tagged with the runway's id:
pnpm runway runway 4 16x9 level4-rw06 1150 600 1420 625
#   → tells you if level4-rw06 already exists (shows current values to diff
#     against) and prints masterX1/Y1/masterX2/Y2 to paste in

# 3. Optionally measure the runway's width (short-axis extent) with two
#    points across the narrow side, then pass them as extra args:
pnpm runway runway 4 16x9 level4-rw06 1150 600 1420 625 1150 560 1420 605
#   → same output plus masterWidth: <value> appended

# 4. Sanity check the position lands correctly on every other generated ratio
#    (verify only checks one point at a time — run it for each endpoint):
pnpm runway verify 4 <masterX1> <masterY1>
pnpm runway verify 4 <masterX2> <masterY2>
#   → prints the projected pixel position on every ratio; open each image
#     and confirm both endpoints land on the runway's two threshold ends
```

You can click on any ratio's image, not just 16x9 — pass that ratio as the
second argument. 16x9 is usually easiest since it's the un-zoomed baseline.

### Runway width

Runway width is the short-axis extent in master-image pixels, authored as
`masterWidth`. At runtime `GameScene` converts it to world units by multiplying
by `sy` (the Y scale factor from the crop rect), which is the correct approach
for a runway's short dimension. Previously this used the geometric mean of the
X/Y scale factors as an approximation — `masterWidth * sy` is now the exact
method. Use `pnpm runway size` to measure it, or pass the two width-point
coordinates as extra args to `pnpm runway runway` (see above).

### Runway dimensions (sizing, not positioning)

Minimum safe `length`/`width` values by aircraft type, for reference when
checking whether a runway's derived length looks right against what's
painted:

| Aircraft type in level | Sprite width (approx.) | Runway length | Runway width |
| ---------------------- | ---------------------- | ------------- | ------------ |
| Type 1 (Cessna)        | ~100 px                | ≥ 300         | ≥ 18         |
| Type 3 (A320)          | ~106 px                | ≥ 320         | ≥ 22         |
| Type 2 (A380)          | ~216 px                | ≥ 480         | ≥ 40         |

If the A380 appears to overshoot the drawn runway, move the runway's
threshold points further apart on the master image rather than editing a
`length` value directly — length is derived now, not authored.

### If you don't have masterX1/Y1/X2/Y2 yet (fallback)

`GameScene.ts` falls back, in order: single-point `masterX`/`masterY` (+
optionally `masterLength`, scaled by an approximate average factor — only
exact on the ratio it was tuned against, since it can't correct for
non-uniform stretch without a second point) → plain `centerX`/`centerY`
fractions (0–1 of the 1920×1080 world, only exact on 16x9). Both exist so a
level isn't completely broken while you're still authoring it — don't ship a
level relying on either; migrate every runway to the two-endpoint form
before release.

## Adding a new level — checklist

- [ ] Create the master background at exactly **1920 × 1080 px** (or larger — the
      build script center-crops per ratio; see `mobileZoom`/`mobileRatios` in
      `process-backgrounds.config.json` for how much extra it needs on the sides)
- [ ] Drop it in `raw_assets/level-N-master.png`
- [ ] Run `pnpm build:levels` — generates every ratio/dpr/format variant + `manifest.json`
- [ ] Use `pnpm runway runway <level> 16x9 <runwayId> <x1> <y1> <x2> <y2>` for
      each runway's two threshold ends (see "Placing runways on the
      background" above) — no per-ratio measuring, no separate bearing step
- [ ] Use `pnpm runway verify <level> <masterX> <masterY>` on both endpoints
      to confirm each runway lands correctly on every generated ratio
- [ ] Add the level entry to `levels.config.ts` with `masterX1`/`masterY1`/
      `masterX2`/`masterY2` per runway (and `masterWidth` if you measured the
      short-axis width with `pnpm runway size` or via the extended `runway` command)
- [ ] Run the game and toggle the debug overlay to confirm collision circles align with runways
- [ ] Test on a tall-screen device (or browser resized to 20:9) to confirm art extends properly

## Common mistakes

| Symptom                                                       | Likely cause                                                                                                                                                                                                                      |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runway collision circle doesn't align with the painted runway | Endpoints hand-converted instead of using `pnpm runway runway`, or the runway is still on the single-point/fraction fallback (16x9-only accurate)                                                                                 |
| Background has black bars on phone                            | Missing tall-ratio variant; fallback 16×9 is letterboxed instead of extended                                                                                                                                                      |
| Background looks squashed/stretched                           | Canvas exported at wrong dimensions (e.g. scaled 16×9 to 20×9 instead of extending canvas)                                                                                                                                        |
| Runway off-screen on ultra-wide                               | Runway too close to left/right edge on 16×9 design; move it inward                                                                                                                                                                |
| Runway right on 16x9 but drifts/rotates on other ratios       | Still using single-point `masterX`/`masterY` (+ `masterLength`) or the `centerX`/`centerY` fraction fallback instead of both endpoints — see "Placing runways" above for why a single point can't correct for non-uniform stretch |

## File format and optimisation

- **Format**: PNG for pixel-perfect maps with transparency; JPG for photographic skies (< 1 MB target).
- **Transparency**: Not required for backgrounds (the background fills the world rect completely).
- **Compression**: Run `pngquant --quality=80-90 level-N.png` or equivalent before committing.
  Unoptimised 1920×1080 PNGs can be 3–5 MB; after compression typically 300–600 KB.
- **Colour profile**: sRGB. Strip ICC profiles to reduce file size.
